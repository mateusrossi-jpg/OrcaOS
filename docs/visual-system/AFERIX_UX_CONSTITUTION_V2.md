# AFERIX UX CONSTITUTION V2
**SCROLL-FIRST EXECUTION MODEL**

**Status:** FROZEN CONSTITUTION
**Objetivo:** Eliminar definitivamente a sensação de ERP tradicional. Transformar o Aferix em um sistema operacional de campo rápido, intuitivo e utilizável com uma única mão.

⸻

## PRINCÍPIO MESTRE
O usuário não deve navegar.
O usuário deve avançar.

Sempre que o usuário estiver executando uma tarefa operacional, o fluxo deve acontecer naturalmente através de scroll contínuo.
O usuário nunca deve ser forçado a trocar de abas para concluir uma atividade.

⸻

## REGRA DE OURO: EXECUÇÃO = SCROLL
Se o usuário está produzindo trabalho:
* Executando OS
* Executando PMOC
* Executando Checklist
* Registrando Anomalia
* Criando Proposta
* Aprovando Serviço
* Assinando Documento
* Finalizando Atendimento

A interface obrigatoriamente deve seguir o modelo:
`SCROLL → AÇÃO → SCROLL → AÇÃO → RESULTADO`

⸻

## PROIBIÇÃO EXPLÍCITA
É proibido dividir fluxos operacionais em múltiplas abas.
Exemplos proibidos:
❌ Aba Dados
❌ Aba Checklist
❌ Aba Fotos
❌ Aba Assinatura
❌ Aba Aprovação

⸻

## MODELO OFICIAL DE PROPOSTA
O usuário deve percorrer a proposta como uma narrativa. Não como um formulário burocrático. Tudo em scroll contínuo.

* **BLOCO 1:** Problema Encontrado (Foto, Descrição)
* **BLOCO 2:** Solução Recomendada (Texto Técnico, Recomendação)
* **BLOCO 3:** Materiais (Peças, Quantidade, Valor)
* **BLOCO 4:** Mão de Obra (Horas, Equipe, Valor)
* **BLOCO 5:** Deslocamento (Custos Extras)
* **BLOCO 6:** Resumo Financeiro (Subtotal, Impostos, Total)
* **BLOCO 7:** Ação (`[ GERAR PROPOSTA ]`)

⸻

## EXECUTION COCKPIT (Nova Regra)
O Cockpit não é Dashboard. O Cockpit é Lista de Trabalho.
Ao abrir uma OS, mostrar imediatamente:
* Progresso
* Próximo ativo
* Lista de ativos

**Ocultar:** KPIs, Métricas, Cards decorativos, Informações secundárias.

⸻

## CHECKLIST ENGINE (Nova Regra)
Cada ativo deve exigir o menor número possível de toques.
**Meta:** 1 ativo conforme = 1 toque
**Fluxo:** `[ MARCAR TUDO CONFORME ] → Auto Save → Próximo Ativo`

⸻

## AUTO SAVE
Obrigatório. É proibido exigir `[ SALVAR ]` durante execução operacional. Toda alteração deve persistir automaticamente.

⸻

## PRINCÍPIO DA CONTINUIDADE
Após concluir uma etapa, o usuário deve ser levado automaticamente para a próxima.
* Nunca retornar para menus intermediários.
* Nunca retornar para dashboards.
* Nunca retornar para listas desnecessariamente.

⸻

## CLIENT PORTAL
Estrutura oficial (Sem navegação, sem menus, sem distrações):
`Resumo → Anomalia → Fotos → Solução → Valor → Assinatura → Aprovação`

⸻

## EXPERIÊNCIAS SEGREGADAS

### OWNER EXPERIENCE
**Exceção autorizada.** O dono não executa. O dono analisa.
Portanto: Cards, Dashboards, KPIs, Gráficos e Múltiplas áreas são permitidos.

### FIELD EXPERIENCE
O técnico executa.
Portanto: Scroll, Botões gigantes, Auto Save, Haptic Feedback e Thumb Zone são obrigatórios.

⸻

## TESTE DE APROVAÇÃO
Nenhuma tela poderá ser aprovada se:
1. Exigir zoom.
2. Exigir duas mãos.
3. Possuir botões menores que 56x56.
4. Possuir mais de uma ação principal.
5. Exigir troca de abas para concluir um processo.

⸻

## MÉTRICA DE SUCESSO
Ao olhar uma tela, o técnico deve entender em menos de 3 segundos:
1. O que estou fazendo?
2. O que faço agora?
3. O que acontece depois?
*(Se não atingir esse critério, a tela deve ser redesenhada.)*

⸻

**MANTRA OFICIAL:**
> "O usuário não navega. O usuário avança. Cada toque deve aproximá-lo do resultado final."
